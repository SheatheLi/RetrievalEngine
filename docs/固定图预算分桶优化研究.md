# 固定图形状预算下的填充代价优化

## 技术内核
`torch.compile(dynamic=False)` 对不同注意力序列长度生成不同的 shape-specialized 图。若编译图数量有硬预算，直接使用 2 的幂补齐长度可减少图数量，但会浪费被注意力计算处理的 Token。

把这个问题映射到**加权一维最优分段**，而不是新增启发式。如果不同实际长度为排序序列 `v[1..N]`，频率为 `f[i]`，最多使用 `K` 种图形状，那么一个区间 `[i,j)` 的填充代价等于 `end(j) * Σ f[i..j)`。用动态规划求精确最优划分；若部署方声明最大可支持长度 32，则最后一桶强制取 32，避免下一个长度 32 产生第 K+1 张图。

## 可复验结果
`src/bucket_optimizer.py` 是 O(KN²) 动态规划；`tests/test_bucket_optimizer.py` 用 25 组独立穷举核验最优性。`benchmarks/optimized_shape_tradeoff.py` 用真实 PyTorch 2.10 CPU / SDPA 多头注意力 / FX eager 后端比较固定分桶与优化分桶，两者均实际捕获 3 张计算图。

对本轮十条序列（每条 batch=2）共 328 个有效 token，原固定 `(8,16,32,64)` 处理 416 token，训练数据优化所得 `(9,17,32)` 处理 382 token（减 8.17%），数值输出误差约 1.2e-7。墙钟延迟未稳定改善，**不能写成 GPU、Inductor 或推理性能加速**。

## 真实竞争边界
优势只对被测序列长度频率成立；若流量转向大量长度 8，优化策略可能比固定桶多处理 token。要达到专业 AI/ML/DL 工程结果，必须用训练与冻结未来日志分割确定桶，测量新流量的图缓存 miss、P95/P99、编译累计开销、端到端推理吞吐和峰值显存，使用真实模型与 Inductor/编译后端。不要把 3/3 图个数当独立 Issue 解决。

## 最短接管任务
手写动态规划转移与正确性证明；删除最大支持长度限制、制造长度 32 的四图回退；恢复限制后在有分布变化的未来日志中测量 padding 代价；解释为什么减少 token 不必然降低 CPU 运行时间。
